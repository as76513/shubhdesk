# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

ShubhDesk — internal sales pipeline (Kanban-style CRM) for ShubhShree Knowledge Hub Pvt. Ltd. A Wealth Manager works a lead end-to-end through New Lead → Meeting → Joint Meeting → Deal Closed — there is no handoff to a separate closer role. React + Vite frontend on AWS Amplify Gen 2 (Cognito auth, DynamoDB/AppSync data), sized for a team under 10 people on the AWS free tier.

## Commands

```bash
npm install          # install deps
npx ampx sandbox      # start local Amplify cloud sandbox (Cognito + DynamoDB in your AWS account);
                      # writes amplify_outputs.json — required before `npm run dev` will work
npm run dev           # Vite dev server (in a second terminal, alongside the sandbox)
npm run build         # tsc -b && vite build
npm run preview       # preview the production build
npm run sandbox       # alias for `ampx sandbox`
```

There is no lint or test script configured in `package.json`. `tsc -b` (part of `npm run build`) is the only type-checking step.

The app cannot run without a live sandbox: `src/main.tsx` imports `../amplify_outputs.json`, which only exists after `npx ampx sandbox` has run at least once and is regenerated (hot-reloaded) whenever the `amplify/` schema changes.

## Architecture

**Two-sided app: `amplify/` defines the backend-as-code, `src/` is the entire frontend.**

- `amplify/auth/resource.ts` — Cognito user pool, email login, no self-signup (`hideSignUp` in the UI). Three groups: `admin`, `wealth_manager`, `advisor`. Staff accounts are created by hand in the Amplify console, one group each.
- `amplify/data/resource.ts` — the data model and, critically, the **authorization rules that enforce the business logic server-side**: `Lead` has an `owner` field (who currently controls it) and a separate `sourcedBy` field (who originally created it, set once). `allow.ownerDefinedIn('owner')` grants full read/write to the current owner; `allow.ownerDefinedIn('sourcedBy').to(['read'])` gives the original creator permanent read-only visibility if ownership is ever reassigned. This is enforced server-side, not just a UI convention — AppSync/Cognito reject writes from a non-owner even if the client were bypassed. In practice `owner` never changes after creation today (`moveStage()` does not reassign it — see below), so this rule mostly exists for any future/manual reassignment. `Lead.email` is optional and is not collected on New Lead. `meetingLocation` and `jointWith` record where the call happened and which colleague joined; entering Joint Meeting does not change `owner`.
- `amplify/backend.ts` — wires `auth` + `data` together via `defineBackend`.
- `Trade` (in `amplify/data/resource.ts`) is a **fully standalone** model — not related to `Lead` at all. It's the entire data surface for the `advisor` role: `clientName`, `buyingLot` (free text — instrument + quantity, advisor's own shorthand, deliberately not a structured field), `brokerage` (integer, ₹), `owner`, and `accountOpenedBy` (`OWN` or a Cognito username — persist the string; do not send `null`, Amplify skips it). Auth is `allow.group('admin')` + `allow.ownerDefinedIn('owner')` + `allow.ownerDefinedIn('accountOpenedBy').to(['read'])` — an advisor only ever sees their own trades; the named opener can read those rows. `src/tradeClient.ts` is the CRUD client for it, mirroring `leadClient.ts`'s pattern but intentionally not reusing any of its code, since the two models don't share anything.
- `src/revenue.ts` — **source of truth for business formulas** (NCA / AUM / SIP / Insurance actuals, trading splits, insurance 50%, date ranges). Documented in [README.md](./README.md#how-numbers-are-calculated). Change the constants there (`TRADING_PLATFORM_FEE`, `ADVISOR_SHARE_OF_COMPANY`, `ADVISOR_OPENED_ELSEWHERE_CUT`, `INSURANCE_WEALTH_MANAGER_SHARE`, `DEFAULT_COMPANY_TARGETS`) and the rest of the app follows.
- `src/leadClient.ts` — the only place that talks to the Amplify Data client (`generateClient<Schema>()`). All reads/writes for `Lead`, `Note`, `StaffProfile`, `Counter` go through here. Notable behaviors:
  - `getMe()` derives the caller's `role` from the Cognito `cognito:groups` claim (`admin` > `advisor` precedence; anyone in neither group defaults to `wealth_manager`).
  - `nextClientCode()` uses a per-month `Counter` row to generate sequential `SSKH-YYMM-NNN` codes.
  - `moveStage()` updates `stage`, and — when moving into `joint_meeting` with a `jointWith` given — stores `jointWith` + `meetingLocation` and stamps `handoffAt` the first time this happens (`owner` does not change; this only records who joined the call and where). It also stamps `closedAt` when entering `closed` (clears it if the lead leaves closed) and `rejectionReason` when the new stage is `rejected` — monthly NCA/AUM/SIP and the CSV use `closedAt`/`handoffAt`, not Amplify's `updatedAt`. The note text is built entirely inside `moveStage()` itself — it does a fresh `listStaff()` lookup right there to resolve people's names (e.g. "Joint meeting with Anita by Amol (meeting → joint_meeting)"), deliberately *not* a resolver function passed in by the caller, so it can never show a stale name (e.g. a colleague whose `StaffProfile` was auto-created moments ago in another tab). Stage ids appear in the text as their raw enum value (`new`, `meeting`, ...), not a pretty label from `App.tsx`'s `STAGES` — this is intentional: looking up a pretty label risks silently mapping a legacy/removed stage id to the wrong label (e.g. falling back to "New Lead"), where the raw id is always honest. **Only affects notes written after this was added**; existing note text with baked-in raw Cognito IDs (from before *any* name-resolution existed) can't be fixed retroactively since it's stored free text, not a lookup (unlike `Note.author`, see below). Note: `Lead.handoffAt` and the owner-vs-`sourcedBy` divergence it can signal (`ownerHandoffs` in `src/report.ts`) exist for historical/manual-reassignment cases, but the app itself never reassigns `owner` today.
  - `friendlyError(e, fallback)` turns a raw GraphQL error array / `Error` into a plain-language message with the technical detail appended — used by every catch block in `App.tsx` so error banners are shareable with support instead of generic "couldn't do X" text.
  - `ensureOwnStaffProfile(role)` — call once per login, right after `getMe()`. Creates a `StaffProfile` row for the current user if none exists, using the email's local part as `displayName`. This is why `StaffProfile` needed a new `allow.ownerDefinedIn('username').to(['create','update'])` auth rule (previously admin-only writes) — a user may only create/update the row matching their own identity. Fixes the recurring "shows up as a raw Cognito ID" problem (people-pickers, card owner names, advisor breakdown) without an admin having to manually seed a row first.
- `src/App.tsx` — the entire UI (board/list/follow-ups views, lead drawer, new-lead modal) as one file, inline-styled (`S` style object + a `CSS` template string), no component library beyond `@aws-amplify/ui-react`'s `Authenticator` and `@dnd-kit/core` for the board. Role-based visibility is re-derived client-side (`visibleLeads`, `canEdit`) purely for UX — the actual enforcement is server-side per above, so client-side checks here are a convenience, not a security boundary.
  - `requestMove()` is the single entry point for moving a lead to a new stage — both the drawer's stage buttons and the board's drag-and-drop call it, so the stage-transition branching logic lives in one place, not duplicated. It routes into `jointPrompt` state (a modal at the `App` level, not inside the drawer) whenever the target is `joint_meeting`, asking who the owner went with (`jointWith`) and where (`meetingLocation`); it routes into `rejectPrompt` state whenever the target is `rejected`. Neither prompt changes `owner`.
  - The board (`Board`/`DroppableColumn`/`DraggableLeadCard`) uses `@dnd-kit/core` with separate `MouseSensor` (distance-activated, so a plain click still opens the drawer) and `TouchSensor` (delay-activated, so a quick swipe still scrolls) — native HTML5 drag-and-drop was tried first and dropped because it doesn't respond to touch at all.
  - `LeadDrawer` shows "→ Proceed to Meeting" / reject on `new`, "→ Proceed to Joint Meeting" / reject on `meeting`, and "→ Deal Closed" / reject on `joint_meeting`. Rejected is an outcome, not a board column — it still goes through `requestMove` into a `rejectPrompt` modal for a **mandatory** one-click reason (`Lead.rejectionReason`, no skip option). The reason shows as a red pill next to the stage pill in the drawer; rejected leads appear in List, not on the board.
  - `Lead.source` is captured once, at creation, via a plain `<select>` on the New Lead form defaulting to `cold_call` — deliberately optional and pre-filled so it adds zero data-entry friction. `SOURCES`/`REJECTION_REASONS` in `App.tsx` mirror the `source`/`rejectionReason` enums in `amplify/data/resource.ts`, same duplication pattern as `STAGES`.
  - Admin can delete a lead from the drawer (`deleteLead` in `leadClient.ts`): all notes for that `leadId` first (paginated so none are left behind), then the lead, after a confirmation that shows client code + name. Trade delete and insurance-entry delete use the same `ConfirmDelete` modal (client + ₹ / employee + ₹ + date) so a tap cannot wipe a row.
  - Phone layout (≤720px): `.stackStrip` stacks progress + incentive; `.dataRow` turns wide lists into labeled cards; header wraps and Sign out uses `.ghost.onDark`. Do not put a desktop-only flex table on trades without `dataRow` / `dataHead`.
- `src/main.tsx` — Amplify configuration + the Cognito `<Authenticator>` login gate wrapping `<App>`, with a custom navy/gold theme. Sign-in / forgot-password accept the email local part (`amol.shinde`); `toCognitoEmail` appends `@shubhshreeknowledgehub.com` before `signIn` / `resetPassword`. Same user pool — no username-alias change.
- `src/report.ts` — the admin-only employee activity report (CSV download). Pure client-side aggregation over already-loaded `App.tsx` state. `tradesToCSV()` is Date, Advisor, Client, Lot, Account Opened By, raw Brokerage — no calculated company/advisor ₹. Employee report Revenue Actual / Incentive Earned sum admin-entered `FinanceEntry` rows, not trade splits.
- **Advisor role**: same Lead pipeline and **PersonalTargetStrip** as Wealth Manager, plus a **Trades** tab (trade log only — no advisor/employee payout tiles). Incentive on the strip is admin-entered (`FinanceEntry`).
- **Weekly targets & incentives**: `CompanyTarget` (`periodType` monthly/quarterly/yearly) holds NCA / AUM / SIP / Insurance **individual quotas** — same numbers for every Wealth Manager, not a company pool. Admin sets them on the Targets tab under collapsible **Individual quotas** (closed by default). **Employee progress** there is one card per Wealth Manager/Advisor; Monthly/Quarterly/Yearly **radios** show only one cadence at a time, and the heading must match that period. The pipeline shows **Company targets** (per-person quota × headcount, unique company actuals) — do **not** put per-person strips on the pipeline. Wealth Manager/**Advisor** see **PersonalTargetStrip** plus **This Month's Incentive** (admin-entered `FinanceEntry`, not calculated from trades). Company pipeline headcount stays Wealth Manager only. CRUD is `src/targetClient.ts`. Do **not** rename `CompanyTarget` (Amplify would create a new table). Keep `periodType` as a string key; valid values are enforced in `upsertCompanyTarget`. Admin Targets also has **AUM Tracking**, **Revenue**, and **Incentive** ledgers (`FinanceEntry`).

**Top stat bar**: Total Leads / Active / Closed Won / **Revenue** (admin-entered `FinanceEntry` kind `revenue` for the current calendar month). Admin also gets **Total Brokerage (till date)** — sum of all `Trade.brokerage`, not this month only. No advisor/employee payout. Wealth Manager/Advisor see `PersonalTargetStrip` plus admin-entered monthly incentive. A centered **Hello {first name} 👋** sits above the stat bar.

**Trades period downloads**: `TradesView` period pills drive trade count and CSV. Admin sees **Total Brokerage** and **Company Revenue** (brokerage − 20% platform). No advisor/employee payout tiles. **All Trades** is sorted by `createdAt` descending (newest first).

**Stages** (`STAGES` in `App.tsx`, mirrored by the live values in the `stage` enum in `amplify/data/resource.ts`): `new → meeting → joint_meeting → closed`. Follow-up, Deal In Progress, and Rejected are **not** board stages. `followup` / `inprogress` / `rejected` stay in the GraphQL enum so existing DynamoDB items still read; the board maps leftover `followup`/`inprogress` rows onto Joint Meeting (`boardStageId`) and leaves rejected off the board (List still sees them). Entering `joint_meeting` opens the `jointPrompt` modal for `jointWith` + `meetingLocation` — it does **not** reassign `owner`; one person works a lead from `new` through `closed`. Moving into `closed` still stamps `closedAt` for NCA/AUM/SIP. The board grid is 4 columns (`repeat(4, ...)` in the `.board` CSS class) — update that alongside `STAGES` if the stage count changes again. Each column header's lead count (`S.colCount`) is tinted to that stage's own color (not a flat neutral) and is always live-derived from `items.length` in `Board` — never a separately maintained counter.

**Follow-ups / win-back**: `followUpOn` (date) on a `Lead` drives the "Follow-ups Due" view — leads with a due date on or before today, for reconnecting with dormant/rejected clients.

When changing the data model, edit `amplify/data/resource.ts` and keep the sandbox (`ampx sandbox`) running so the schema and generated types hot-reload; `src/leadClient.ts` and `src/App.tsx` consume `Schema['Lead']['type']` etc. directly from that file. See [SCHEMA_DESIGN.md](./SCHEMA_DESIGN.md) for the full data model, access patterns (query vs. scan), and a checklist for adding fields/queries without accidentally introducing an unindexed scan.

## Deployment

Full deployment steps (Amplify Hosting, custom domain via GoDaddy, adding staff/roles) are in [DEPLOY.md](./DEPLOY.md). Notably: every push to the connected branch (`main`) auto-deploys via Amplify Hosting. Staff only need a Cognito user created (console) — their `StaffProfile` row is now auto-created on first login via `ensureOwnStaffProfile()` (see above), not a required manual step. **`StaffProfile.username` must be the user's actual Cognito `Username`, which is an auto-generated ID (a UUID), not their email** — this pool is configured with `usernameAttributes: [email]` for *sign-in*, but Cognito still assigns a random Username under the hood, and that's what `getCurrentUser().username` returns and what `owner`/`sourcedBy` get set to. Look it up on the user's detail page in the Cognito console if you need to manually edit a profile's `displayName`.
